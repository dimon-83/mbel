# Review of 0002-modu-host-import.md (external write-path integration findings)

- **Status:** Completed review — accept with revisions
- **Date:** 2026-11-03
- **Reviewer:** mbel maintainer side (requested by the embedder)
- **Subject:** `docs/proposals/0002-modu-host-import.md`
- **Method:** full source re-read (not from memory); every claim below was re-verified against the tree, with one web check of the mooncakes registry for decimal/crypto availability

## Verdict

0002's **thesis survives review**: the dotted-namespace verdict is correct and
final; M1 (host step) needs nothing from this repo; M2's strict-pure
precondition is *implementable with existing checker machinery* — cheaper than
0002 itself estimates. But the proposal's numeric model is **factually wrong in
three places**, and the errors are load-bearing: they misstate what the
language can guarantee, they mis-place where the precision gap actually lives
(the JSON boundary, not the value model), and they cause M3 to dispose of the
wrong thing. Accept **after** the must-fix list below; none of the fixes
overturn a decision, but M3's disposition changes from "non-goal" to
"deferred, with two cheap language-side items pulled out of it".

### Must-fix list (for 0002)

1. **Fix the value-model facts (§1 table, §2 gap #5, M3, Appendix A note).**
   `Value` has both `NumVal(Double)` and `IntVal(Int64)` (`ast/ast.mbt:28-48`);
   the standard dialect produces `IntVal` for integer literals and pure-integer
   arithmetic (Int64 wrap, Go semantics), promotes int+float→float
   (`evaluator/evaluator.mbt:390-398`). "Bitwise is the only Int64 round-trip"
   is false (`builtin/bitwise.mbt:27-33` returns `IntVal`, and integer
   arithmetic stays `IntVal`). "No bigint" should read "no arbitrary
   precision"; Int64 exists as a first-class runtime value in the expr dialect.
2. **Re-locate the decimal gap.** The dominant loss point is not the value
   model but the **JSON boundary, both directions**: input maps *every* JSON
   number to `NumVal(Double)` (`playground/web/web.mbt:159`), discarding
   integer-ness that MoonBit core's JSON lexer preserves up to 2^53 (core
   `json/lex_number.mbt` keeps `Ok(i)` for `|i| <= 2^53-1`); output converts
   `IntVal` via `to_double()` with the in-source admission "int64 beyond 2^53
   loses precision in JSON … documented divergence until a typed JSON writer"
   (`builtin/helpers.mbt:189-200`). Secondary loss points: `/` is always float
   division (`expr/check.mbt:569-575`, `evaluator/evaluator.mbt:447-454`), `**`
   is always float (`expr/check.mbt:625-631`), `mean`/`median` are double
   (`builtin/builtin.mbt:111-139`).
3. **Add a missed gap: division by zero is silent ±Inf.**
   `evaluator/evaluator.mbt:448-449` — "expr: `/` is always float division
   (7/2 = 3.5, 1/0 = +Inf); no divide-by-zero error." A ratio-style judge rule
   (`x / y > 0.5` with `y == 0`) evaluates **true**. For a write-path rule
   engine this is a correctness hazard, independent of the decimal question;
   it belongs in §2's gap list and in modu's rule-writing discipline, and a
   divide-by-zero error (opt-in or standard-dialect) is a candidate 0.4 item.
4. **State the checker's structural env-blindness where it matters.** The
   checker's own scope note: "Env values, dynamic members and heterogeneous
   containers stay unknown/legal" (`expr/check.mbt:11-15`); `EMember` is
   unconditionally `UnknownN` (`expr/check.mbt:235-238`). `sum`'s static check
   verifies container-ness only, never element nature (`expr/check.mbt:493-520`).
   Consequence 0002 implies but never says: **no language-side checker can
   catch "decimal column accumulated as double" — not today, and not after
   adding a decimal Nature — because column reads are invisible to the type
   layer.** The only enforcement point is host-side schema-aware linting; M0's
   optional TS warning is not optional, it is the whole mechanism.
5. **Fix the 0001 citation.** The three-part objection ("breaks the pure
   sandbox, is not portable to wasm, and makes results non-deterministic
   across hosts") is from 0001 **§9 (Alternatives)**; §7 is the directive
   ("Do not add host callbacks to the wasm ABI"), §3 the non-goal list.
6. **M0-1: account for the caret block.** Compile-mode errors are not just
   "msg (L:C)" — they append `\n | src-line\n | ...^` (`expr/eval.mbt:147-168`,
   `positioned()`). modu's substring parsing must strip or carry the multi-line
   form, or every mapped message embeds source text.
7. **M2 file table: re-point the checker row.** The precondition needs **zero**
   checker changes: `strict_calls` already rejects any callee outside
   `functions`/`callables`/aggregates (`expr/check.mbt:296-298`, mechanism at
   `:156-160`), and the instance checked entry threads `callables` from the
   engine (`expr/eval.mbt:74-105`, assembled at `engine/exprapi.mbt:97`).
   The real surface is engine-side: register `$host` into the instance pool
   **only under the load-time opt-in**, and thread it into `callables` there.
   The `expr/check.mbt` row should be replaced by `engine/exprapi.mbt` (+ the
   existing `engine/userfuncs.mbt` reservation row stays).
8. **Record the ecosystem check.** mooncakes has `moonbitlang/x/decimal`
   (arbitrary precision, `max_scale = 28`, `Decimal::from_double(d,
   precision)`) and a pure-MoonBit crypto lib (`mooncry`, zero-dependency,
   test-vector-verified). The former re-bases M3's cost estimate; the latter
   may undercut M2's cost-benefit if the needed KDF exists natively (see
   Part 3, M2).

## Part 1 — the "strong typing" claim, verified

The static layer is real but deliberately shallow:

- **Type set** (`expr/check.mbt:35-47`): `IntN | FloatN | StringN | BytesN |
  BoolN | NilN | ArrN(Nature) | MapN(Nature) | UnknownN`. No unions, no
  subtyping; "promotion" is not coercion but an operator rule (int∘float →
  float, `check.mbt:553-575`). int and float are **distinct natures** — 0002's
  implicit "number is a single type" is wrong even before decimal enters.
- **What it guarantees** (all with positions, `check.mbt:25-30`):
  mismatched operands are compile errors ("invalid operation: + (mismatched
  types int and string)", `check.mbt:539-560`), non-bool conditions rejected
  (`:374-386`), membership assignability checked (`:637-664`), and — in the
  strict contexts (checked user functions, instance checked entry) — unknown
  *names* and unknown *calls* are compile errors (`:222-233`, `:296-298`).
- **What it structurally cannot guarantee:** anything about data. Bare
  identifiers from env are `UnknownN` (`:222-233`), member access is
  unconditionally `UnknownN` (`:235-238`), heterogeneous containers degrade
  (`:256-284`), and the file's own scope note says so (`:11-15`). There is no
  channel in `CheckCtx` (`:115-124`) to inform the checker of column types —
  it carries function arities and callable names only.

**Verdict on the claim**: "strong typing" is accurate for the
literal-derivation fragment and for call/name governance (which is exactly
what M0-2 and M2's precondition lean on — both verified sound). For *data*,
the checker is a name/arity gate, not a type gate. Any proposal text that
reads as if checked mode could police numeric semantics of column data is
wrong; 0002 flirts with that reading in M3's framing ("checked mode can't
detect it" is stated, but the *reason* — structural env-blindness — and its
corollary — host-side enforcement is the only option — are not).

## Part 2 — decimal / bigint: current state, options, recommendation

### Where integer exactness actually lives and dies

| Stage | Representation | Evidence | Exact? |
| --- | --- | --- | --- |
| Integer literal (expr dialect) | `IntVal(Int64)` | `ast/ast.mbt:31-37` | exact; >int64 literals are parse errors |
| Pure-integer arithmetic | `IntVal`, Int64 wrap (Go semantics, silent) | `ast/ast.mbt:33-36`; `evaluator.mbt:390-393` (`typed_int_arith`) | exact, incl. silent wraparound on overflow |
| int ∘ float | promotes to `NumVal(Double)` | `evaluator.mbt:395-398` | double semantics |
| VM constant pool | `CVal(@ast.Value)` — same values | `evaluator/vm.mbt:22-33` | as above |
| `sum` over integers | stays `IntVal` until a float appears | `evaluator/aggregates.mbt:105-127` | exact for all-int input |
| `sum` over env data | `NumVal` elements → double accumulator | `aggregates.mbt:105-127` | double |
| Bitwise | double→Int64 range-checked, result `IntVal` | `bitwise.mbt:10-33` | input already approximate >2^53 |
| **JSON in (env)** | **all numbers → `NumVal(Double)`** | `web.mbt:159` | **dies here for env data**; core lexes integers ≤2^53 exactly but mbel discards it |
| **JSON out** | `NumVal`→`Json::number(d)`; `IntVal`→`to_double()` | `helpers.mbt:189-200` | **dies here >2^53**; in-source "documented divergence until a typed JSON writer" |
| Division / `**` | always float; `1/0`→`+Inf`, no error | `check.mbt:569-575`, `625-631`; `evaluator.mbt:447-454` | float |

So: integers > 2^53 stay exact only inside pure-literal integer arithmetic
and bitwise; **env-sourced integers never get integer treatment at all** (the
boundary double-maps them), and integer results lose exactness again on the
way out beyond 2^53. There is no arbitrary-precision anything: 2^63 is the
ceiling, and only in the corners above.

### Options, costed

| Option | Covers | Change surface | Cost | Risk / residual |
| --- | --- | --- | --- | --- |
| **(a) minor-integer-unit discipline + host lint** (M3 as amended) | add/sub/mul/comparisons on cent-integers ≤ 2^53 (doubles are exact there); storage stays int columns | modu-side only: schema-aware lint (warn on `sum`/`avg`/`/`/`**` over decimal-typed columns), rule-writing rules | days; zero wasm risk | division/percentage/avg necessarily float — must round deliberately; `x/y>0.5` with y=0 is **true** (Inf) — needs explicit guards; fractional input data breaks the discipline silently unless schema-enforced |
| **(d1) integer-exact JSON boundary** | env integers ≤2^53 become `IntVal`; typed output writer for `IntVal` | `web.mbt` `json_to_value` one match arm (core Json already carries the integer); output via the "typed JSON writer" the source already names as missing | small; wasm rebuild + sha256 + conformance anchors | mixed int/float data changes arithmetic natures seen by checker/runtime — needs a conformance sweep; does nothing for fractional money |
| **(d2) divide-by-zero → error** | kills the silent-Inf hazard for judge rules | `evaluator.mbt:447-454` (+ checker note) | small; same release overhead as d1 | changes documented expr-parity semantics (`1/0 = +Inf` mirrors expr) — needs a parity-contract decision (`docs/parity-contract.md`) |
| **(c) hybrid decimal**: `DecVal` variant + `dec("12.30")` builtin + decimal∘decimal arithmetic + exact out; **no** checker Nature, mixing decimal with float rejected | genuinely fractional money (rates, tax, FX) with exact semantics; deterministic, no host dependency | `ast`, `evaluator` ops, `aggregates` (decimal accumulator), one builtin, JSON writer (string-tagged or typed), conformance both engines; reuse `moonbitlang/x/decimal` (mooncakes: arbitrary precision, max_scale 28) instead of hand-rolling | medium — a focused 0.x release, not a patch | boundary protocol is the hard part: JSON has no decimal — values must arrive string-tagged + `dec()` parse, which is a DSL decision, not just a value type; env-blindness applies to decimal too (column reads stay `UnknownN`) |
| **(b) full language decimal** (static or dynamic scale as first-class Nature) | everything (c) covers, plus literal-derived decimal typing in checker | everything (c) touches **plus** `Nature::DecN` + operator/promotion lattice in `check.mbt` + both engines' natures + docs | large — a language revision across checker/VM/evaluator/ABI | static scale is nearly pointless while env reads are `UnknownN`; the checker would only ever type literals — same blind spot, much more machinery |

**The decisive observation**: language-side decimal does **not** fix modu's
actual enforcement problem. The checker cannot see column types
(Part 1), so "this decimal column is being double-accumulated" is unenforceable
in the language *regardless of which option ships* — modu needs schema-aware
linting in all worlds. The choice between (a) and (c) is therefore purely
about arithmetic exactness needs, not about governance.

### Ordering and disposition

1. **modu now**: (a) — integer discipline + schema-aware lint at the host.
   This is the minimal viable answer; it is days of host work and no wasm risk.
   Rule-writing rules must additionally mandate the two guards (no `==` on
   computed floats; no unguarded division).
2. **mbel 0.4 candidates** (cheap, orthogonal to M2): (d1) integer-exact
   boundary + typed `IntVal` writer — the source already names the writer as a
   known divergence; (d2) divide-by-zero error behind a parity decision. Both
   are small, conformance-anchored changes that remove entire classes of the
   (a) residual risk.
3. **Deferred, named trigger**: (c) hybrid decimal, triggered the day modu has
   a hard requirement for fractional money math (rates/tax/FX) that double
   provably cannot carry. Reuse `moonbitlang/x/decimal`; budget it as a
   focused release. **(b) full checker-typed decimal stays a non-goal** — it
   buys nothing the env-blind checker doesn't already ignore.
4. **M3's verdict in 0002** ("long-term non-goal") is therefore *half-right*:
   right to refuse (b), wrong to record the gap as "no decimal type" — the
   record must say: Int64 exists, the boundary is the leak, the checker is
   env-blind, the cheap fixes are (d1)/(d2), and the real-money path is (c)
   with a string-tagged boundary.

## Part 3 — verification of the remaining sections

**M0-1 (error positions)** — verified with one correction (must-fix #6):
parse errors are `"parse error at L:C: msg"` (`expr/eval.mbt:23-33`);
compile-mode check errors are `msg (L:C)` **plus** a source line and caret
block (`expr/eval.mbt:147-168`); runtime `EvalErr` carries message only, no
position (e.g. `builtin/bitwise.mbt:17`). 0002's claim and workaround stand.

**M0-2 (builtin reserved list)** — mechanism verified: user functions
upsert into the same pools the engine seeded with builtins, so pool lookup
makes shadowing possible (`engine/engine.mbt:64-72`, resolution at
`evaluator.mbt:1464-1484`); `len` is unshadowable because the expr front end
lowers it to `expr.len`, and those internal names "are not lexable as
identifiers, so a user cannot call them directly" (`builtin/builtin.mbt:617-628`).
The stopgap and its retirement condition (0001 P4) are coherent.

**M1 (host step)** — modu-side; no objection. The determinism rationale is
sound: the wasm's only import is the clock (`builtin/time.mbt`), the evaluator
is otherwise pure, and 0002 keeps it that way.

**M2 (import channel)** — the precondition **verifies as nearly free**
(must-fix #7): `strict_calls` + `CheckCtx.callables` already implement
"reject unless opted in" (`expr/check.mbt:156-160, 296-298`;
`expr/eval.mbt:74-105`; assembly at `engine/exprapi.mbt:97`). Reserving the
name sits in `engine/userfuncs.mbt:81-96` next to `$env`. Two additions from
this review: (i) **re-run the cost-benefit against mooncry** — a
pure-MoonBit, zero-dependency crypto library now exists on mooncakes; if it
covers the KDF modu needs, a wasm-native `$hash_password`-style builtin may
serve the write path with no import channel, no host stubs, and no
determinism carve-out; M2 should record that as the first spike, and only
proceed if native coverage is inadequate. (ii) the `hostCalls` budget
question is legitimate: `max_steps` counts evaluator node visits
(`evaluator.mbt:1019-1021`) and cannot bound native work inside one step.

**Budgets claim** (`describe_abi` limits) — verified earlier against
`playground/web/web.mbt:34`; unchanged.

**RE2 / Unicode** — `upper`/`lower` are ASCII-only by implementation, with the
follow-up note in source (`builtin/strutil.mbt:4-5, 16-39`); non-ASCII
characters pass through unchanged (silent, not an error) — 0002 documents
this correctly. The regex reference page exists (`docs/en/regex.md`); 0002's
RE2 remark makes no claim this review could falsify.

**0001 citations** — see must-fix #5.

## Bottom line for the embedder

Proceed with M1 and M0 as written (M0-1 with the caret-block fix). Treat M2 as
*gated on a mooncry spike*, not on extern mechanics — the checker side is
already done. Re-base M3 on the corrected numeric model: integer discipline +
host lint now; integer-exact boundary and divide-by-zero as cheap 0.4
candidates; hybrid decimal as a named-trigger deferred item. None of these
changes the modu P4 plan; they change what 0002 tells P4 about the ground it
stands on.
