# 路线图审核意见(2026-09-06,外部评审)

> 针对 docs/coverage-vs-expr.md 阶段 4 后续路径的外部审核。原文归档如下,
> 采纳情况见 coverage-vs-expr.md §7(逐条标注)。

## 总体结论

这份后续路径梳理基本合理、可实现性判断准确,优先级划分清晰,降级方案务实,
充分考虑了 MoonBit 目标平台与工程约束。
主要技术路线(Lexer/Parser 重写 → 值模型类型化 → Checker → 语义切换 → VM 增强)
符合编译器前端与解释器的典型演进顺序,且与现有测试/差分基础设施的配合方式正确。

## 一、已实现部分

"谓词聚合(15个)"表述模糊:函数式调用形式已实现(如 count(list, predicate)),
而 list[?predicate] 或花括号谓词语法尚未实现。建议明确区分。

## 二、阶段A(P0)

1. Lexer(3~4天):`.5` 需明确 token 边界(与成员访问符 `.` 冲突);
   `not/and/or/matches` 建议上下文相关关键字策略;八进制转义降级需文档化。
2. Parser(10~14天,可能偏 14+):先设计完整 AST 节点类型;Pratt 处理比较链
   (a<b<c 不能简单转二元);方法调用与可选链语法;谓词花括号语法在此阶段
   设计并预留原生聚合循环生成接口。
3. 值模型类型化:设计可与 Parser 并行;工作量可能超 8 天(涉及所有算术/
   比较/位运算/转换函数);降级方案不建议作为首选。

## 三、阶段B(P1)

4. Checker 拆两阶段:第一(4~6天)env 白名单 + 行:列 + 基本运算符检查;
   第二(8~12天)完整类型推断。
5. 语义切换:新 API 尽早定义(内部先委托现有引擎);新旧测试同步。

## 四、阶段C

VM 剩余指令(let 槽/切片/可选链)与 Disassemble 依赖 Parser AST;建议指令
语义与栈操作先行设计,与前端并行。

## 五、可简化或延后

1. 正则:RE2 不支持反向引用,"RE2 全特性"措辞不准,应为"正则全特性";
   800~1200 行估计偏乐观(含解析/编译/NFA/DFA 通常 2000+);范围建议缩至
   字面量/字符类/量词/锚点/分组(非捕获);FFI 方案需明确 API 边界;P2/P3。
2. 时区:UTC+固定偏移降级恰当,完整 tzdata 走外部文件加载接口。
3. 优化器剩余 pass:非紧急。

## 六、无法实现或必须降级

| 功能 | 意见 |
|---|---|
| 大整数任意精度 | 降级合理;需文档明确 Int64 溢出行为(回绕/报错/转浮点) |
| 正则全特性 | 明确不支持反向引用、Unicode 属性、环视;子集是唯一务实选择 |
| 完整 tzdata | 降级合理 |
| toJSON NaN/Inf | 建议保持与 Jexl 一致(返回 null),提供严格模式开关 |

## 七、优先级表

- 花括号谓词语法与 Parser 同一任务,非独立项。
- Checker 拆两阶段降低风险。
- 正则基本子集延后;完整 RE2/tzdata 可永不实现,只留扩展接口。

## 八、风险补充

1. 工作量估计偏乐观 30~50%,每阶段预留 20% 缓冲。
2. 新语法需要配套新增测试与差分样本,与特性同步落地。
3. 性能目标依赖谓词原生循环,需 VM 指令集扩展配合,不能以普通函数调用模拟。
4. legacy 包共存需注意资源隔离(全局状态、错误通道)。
5. 文档同步(用户手册、错误码表)。

## 九、调整后路径

1. 立即启动 Lexer 增强 + Parser 重写(含花括号谓词),并行设计值模型(不实现)。
2. Parser 完成 70% 时:开始值模型类型化,逐步替换 NumVal。
3. Parser 基本可用时:启动 Checker 第一阶段,并定义新 API 接口。
4. Checker 完成后:语义切换到新 API,旧 API 进入 legacy。
5. 核心稳定后:正则子集、优化器其他 pass、时区扩展。

**总结**:整体可行;小步迭代、尽早集成测试、工作量留余地。测试基础设施是
最大优势,务必让新特性全部进入安全网,而不只是回归旧行为。
